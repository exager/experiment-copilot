1. Executive summary

Experiment Copilot turns a product manager's rough idea into a fully reasoned A/B experiment decision. A PM describes a business goal and pain point; the system proposes a testable hypothesis and success metrics, designs a launchable experiment configuration, validates it against a rule book, simulates traffic, runs the statistics, and writes an executive report with a scale / continue / stop / rollback recommendation.

The end-to-end journey

A single experiment moves through seven logical stages, orchestrated by a LangGraph state machine with two human review pauses: 

context  ->  hypothesis  ->  [PAUSE: review metrics]  ->  design  ->  validation
        ->  [PAUSE: review & launch]  ->  simulation  ->  statistics  ->  explanation  ->  report
Core design thesis

The LLM narrates; deterministic Python decides. Every consequential decision — whether a config is valid, who "wins" the test, what the recommendation is — is made by pure, testable code: a JSON-driven rule engine and a SciPy statistics engine. The language model's job is strictly to understand fuzzy input and explain the outcome in plain English. It never re-decides pass/fail. This keeps the product trustworthy, reproducible, and cheap to test, while still feeling conversational.

Why this matters (design pillars)

PillarHow it shows up in the code
Determinism where it countsapp/rules/ and app/statistics/ are pure functions; the same inputs always yield the same decision.
Single source of truthapp/catalog/ defines every metric, audience, and traffic split. Schemas, prompts, simulator, and rules all read from it.
Human-in-the-loopLangGraph interrupt_before pauses let the PM edit metrics and approve launch before anything runs.
Graceful degradationIf Gemini is down or rate-limited, the pipeline still produces a deterministic score and result instead of a 500.
ObservabilityLangSmith auto-traces every LLM call and graph node once a key is set; structured logging everywhere.
Testability without costA deterministic fake LLM drives the whole test + evaluation suite; no API key or network required.

2. High-level architecture

The backend is a layered FastAPI application. Requests enter through thin routers, which delegate to a services layer that owns all persistence and orchestration. The AI pipeline (LangGraph + agents) and the deterministic engines (rules, statistics, simulation) sit beside the services and share the same models and catalog.

flowchart TB Client["Frontend / API client"] subgraph api [API layer - app/api] Routers["context · experiment · validation · metrics · report · catalog routers"] end subgraph svc [Services layer - app/services] Services["context · experiment · hypothesis · validation · metrics · statistics · recommendation · simulation · report"] end subgraph ai [AI pipeline - app/graph + app/agents] Graph["LangGraph state machine"] Agents["6 agent nodes (Gemini)"] Prompts["app/prompts/*.md"] end subgraph det [Deterministic engines] Rules["Rule engine - app/rules"] Stats["Statistics - app/statistics"] Sim["Simulation + scheduler - app/simulation"] end subgraph data [Data + contracts] Models["ORM models - app/models"] Schemas["Pydantic schemas - app/schemas"] Catalog["Catalog - app/catalog"] DB[("SQLite - experiment.db")] end Client --> Routers --> Services Services --> Graph Graph --> Agents --> Prompts Agents --> Rules Graph --> Sim Services --> Rules Services --> Stats Sim --> Stats Sim --> Rules Services --> Models --> DB Agents --> Models Schemas --> Catalog Rules --> Schemas Agents --> Catalog

What each layer is responsible for

  • API (app/api): request/response shapes, HTTP status codes, dependency injection of a DB session and the resolved experiment. No business logic.
  • Services (app/services): every persistence operation and lifecycle transition. Functions take a Session as the first argument; routes and background jobs call them.
  • AI pipeline (app/graph, app/agents, app/prompts): the LangGraph workflow, six agent node functions, and their Markdown prompts.
  • Deterministic engines (app/rules, app/statistics, app/simulation): the trustworthy core — rule evaluation, the two-proportion z-test, and the synthetic traffic generator.
  • Data & contracts (app/models, app/schemas, app/catalog): SQLAlchemy tables, Pydantic validation, and the shared enum/spec catalog.
Why a services layer at all?

Both the API routes and the graph's agent nodes need to persist to the same tables with the same rules (e.g. "editing a hypothesis invalidates a prior validation"). Centralizing that in services means there is exactly one place a state transition can happen, so the manual API path and the AI graph path can never drift apart.

3. Runtime bootstrap & lifespan

app/main.py is the FastAPI entry point. It uses an async lifespan context manager so startup and shutdown are explicit and ordered.

Startup sequence

  1. configure_logging() — installs a single stdout handler and silences chatty third-party loggers.
  2. init_db() — imports the models package (registering every ORM class on Base.metadata) and runs create_all(), creating experiment.db on first boot.
  3. get_scheduler().start() — starts the APScheduler background scheduler.
  4. _resume_running_experiments() — finds any experiment still in RUNNING state and re-registers a per-tick simulation job for it.
Why resume running experiments on startup?

Simulation jobs live only in the in-process scheduler, not the database. If the server restarts while an experiment is RUNNING, its tick job would be lost and the metrics series would silently freeze. Re-registering on startup makes a restart transparent — the DB is the source of truth for "what should be ticking".

Middleware & error handling

  • CORS: wide-open by default for local dev; note that the CORS spec forbids allow_credentials=True with a wildcard origin, so the app flips credentials off when origins is ["*"].
  • TrustedHostMiddleware: restricts Host headers via ALLOWED_HOSTS.
  • AppError handler: a single exception handler converts any AppError subclass into a consistent JSON body ({error, message, details}) with the right status code.
  • GET /health: trivial liveness probe returning {"status": "ok"}.

All routers are then attached via register_routers(app).

4. Configuration & environment

app/config.py has two jobs. First, importing it loads backend/.env into os.environ exactly once (idempotent, and safe when the file or python-dotenv is missing). Second, it exposes a cached pydantic-settings Settings object.

Why load .env on import?

LangChain reads the LANGCHAIN_* vars directly from the environment for automatic tracing, and the Gemini client reads GEMINI_API_KEY. By loading .env the moment app.config is imported (and importing it first inside app/agents/llm.py), every code path — server, tests, eval CLI — boots with a populated environment without each entry point having to remember to do it.

Settings and derived flags

Settings map environment variables through aliases. Two computed properties gate optional behavior: llm_enabled is true only when GEMINI_API_KEY is set, and langsmith_enabled is true only when LANGCHAIN_API_KEY is set. A field validator lets list settings (CORS_ORIGINS, ALLOWED_HOSTS) accept either a JSON array or a comma-separated string.

5. Persistence layer & status lifecycle

Engine & sessions

app/database/session.py builds a module-level engine and SessionLocal factory from DATABASE_URL. For SQLite it passes check_same_thread=False so the APScheduler background threads and FastAPI request handlers can share connections. configure_database(url) can rebuild both against a new URL — tests use this to attach an in-memory database. get_db() is the FastAPI dependency that yields a session and always closes it.

The declarative Base lives in its own module (app/database/base.py) so ORM models can import it without an import cycle back to session.py.

The four tables

ModelTableKey columns
ProductContextproduct_contextsbusiness_goal, website, current_flow, feature, pain_point
Experimentexperimentscontext_id (FK), hypothesis (JSON), configuration (JSON), validation (JSON), status (enum), timestamps
Metricsmetricscumulative per-arm counts, guardrails (JSON), derived stats, recommendation snapshot, timestamp
Reportreportssummary, recommendation, business_impact, next_steps (JSON), details (JSON)

Relationships: a context has many experiments; an experiment has many metrics rows (one per tick, ordered by timestamp) and exactly one report. Cascades delete children with the parent. The metrics table has a composite index on (experiment_id, timestamp) for fast dashboard reads.

Why store hypothesis/configuration/validation as JSON blobs?

These shapes are AI-generated and still evolving. Persisting them as JSON columns lets the agent output and Pydantic schemas change without a database migration. The catalog + Pydantic layer still guarantees the contents are valid; the DB just stores the validated blob.

Status lifecycle

ExperimentStatus (a StrEnum in app/catalog/status.py, kept out of the ORM so graph/services/prompts can reference it freely) drives the whole lifecycle. All transitions live in experiment_service, which refuses illegal moves with a ConflictError (HTTP 409).

stateDiagram-v2 [*] --> draft: create_draft draft --> validated: mark_validated validated --> draft: edit hypothesis/config validated --> running: launch running --> completed: sample size reached running --> stopped: manual stop validated --> stopped: manual stop completed --> [*] stopped --> [*]
Why does editing revert VALIDATED to DRAFT?

update_hypothesis / update_configuration clear validation and drop the status back to DRAFT. A validation result only describes the config it was run against; the moment the PM changes a metric or a split, that verdict is stale, so the system forces a re-validation before launch.

No migrations (by design, for the POC)

The schema is created directly from the models via Base.metadata.create_all() on startup — idempotent, creating only missing tables, never dropping data. This is a deliberate POC trade-off: fast iteration over migration ceremony. A production system would introduce Alembic.

6. Contracts: schemas & the catalog

The catalog is the single source of truth

app/catalog/ defines every value the platform recognizes: metrics, audiences, traffic splits, durations, confidence levels, sample sizes, and statuses. Each MetricSpec carries rich metadata — kind (ratio / currency / duration / count), direction (higher/lower is better), which roles it may play (primary / secondary / guardrail), a baseline value, and a unit.

ConsumerWhat it reads from the catalog
Pydantic schemasValidate that agent-emitted metric ids exist and are used in an allowed role.
Promptscatalog_summary() is injected so the LLM can only choose real ids.
Simulation engineUses kind + baseline to pick a distribution per metric.
Statistics engineUses kind to choose the right test.
Recommendation engineUses direction to define what "regression" means.
GET /catalogServes the whole thing so the frontend can render dropdowns without hard-coding.
Why centralize the catalog?

An LLM left to its own devices emits free-form strings like "Bounce Rate". Downstream code needs stable ids like bounce_rate. By injecting the catalog into the prompt and validating output against it, the model is boxed into emitting exactly the ids the simulator, statistics, and rules understand. One list changes behavior everywhere consistently.

Pydantic schemas enforce the contract

app/schemas/experiment.py is where the catalog is enforced. Hypothesis validates that primary_metric is primary-eligible, secondary/guardrail ids are valid for their roles, and the primary isn't duplicated as a secondary. ExperimentConfiguration constrains audience to the Audience enum and derives the concrete traffic_split fractions automatically from the chosen traffic_split_option.

Why derive traffic_split from an option?

A free-form pair of floats can be inconsistent (e.g. 0.6 / 0.5). By choosing a named preset (50_50, 90_10, …) and computing the fractions in a model validator, the split is always internally consistent and always sums to 1.0 — which is exactly what the validation rule engine later checks.

Other schema groups: validation.py (RuleResult, ValidationResult with optional AI-enriched validation_score/warnings/suggestions), metrics.py (StatisticsOut, RecommendationOut, MetricsSnapshot for the dashboard), hypothesis_review.py (the interrupt payloads, covered in section 10), and agent_outputs.py (LLM-only "narration" schemas that don't map to DB fields).

7. The LangGraph pipeline

The heart of the system is a LangGraph StateGraph assembled in app/graph/builder.py. It chains eight nodes, keeps state in a shared TypedDict, checkpoints to memory, and pauses at two human-review points.

flowchart TD START([START]) --> ctx["context_agent"] ctx --> hyp["hypothesis_agent"] hyp -. "INTERRUPT #1
review metrics" .-> design["experiment_design_agent"] design --> val["validation_agent"] val -. "INTERRUPT #2
review & launch" .-> sim["simulation_node"] sim --> stats["statistics_node"] stats --> expl["explanation_agent"] expl --> rep["report_agent"] rep --> ENDN([END]) ctx:::llm hyp:::llm design:::llm val:::llm expl:::llm rep:::llm sim:::det stats:::det classDef llm fill:#eaf0ff,stroke:#2b5cff; classDef det fill:#eefaf1,stroke:#7dcf9a;

Blue = LLM agent nodes · Green = deterministic nodes. Dotted edges are interrupt_before pauses.

Shared state

app/graph/state.py defines ExperimentState, a total=False TypedDict. Input fields (business_goal, website, …) mirror the product context. experiment_id / context_id are present only on the persisted, API-driven path (absent when unit tests call a node directly). Each node then fills in exactly one output key, in pipeline order: context_understanding, hypothesis, configuration, validation, metrics, statistics, recommendation, report, plus an errors list.

Checkpointing and the two interrupts

The graph is compiled with a MemorySaver checkpointer and interrupt_before=["experiment_design_agent", "simulation_node"]. That produces two pauses:

  1. After hypothesis_agent (before design): the PM reviews and edits the proposed success metrics.
  2. After validation_agent (before simulation): the PM reviews the validated configuration and explicitly launches.
Why a checkpointer + thread_id?

Human-in-the-loop means the graph must stop, hand control back to the API, and later resume from the exact same spot — possibly across separate HTTP requests. The MemorySaver persists each thread's state keyed by a thread_id (the experiment id as a string). The API can inspect a thread (get_state), patch it (update_state, to apply the PM's metric edits), and resume it (invoke(None, config)) without re-running any completed node.

The four graph helpers

HelperRole
start_experiment(thread_id, state)Run from START to the first pause (produces the hypothesis review).
resume_experiment(thread_id)Resume from whichever interrupt the thread sits at (design+validate, or simulate→report).
update_experiment_state(thread_id, values)Patch checkpointed state (e.g. the edited hypothesis) before resuming.
get_experiment_snapshot(thread_id)Inspect a thread; .next is falsy when it never started or already finished — used to tell a graph-driven experiment from a manual one.
Why the simulation and statistics nodes are deterministic

app/graph/pending_nodes.py holds simulation_node and statistics_node. Instead of waiting on wall-clock ticks, simulation_node loops the same run_one_tick the live scheduler uses — synchronously, inside a single resume — until the sample size is hit, writing real Metrics rows. statistics_node then computes the snapshot and adds sample_ratio and guardrail_regression so the recommendation rules can reach the rollback / stop paths.

8. Agents, prompts & the LLM factory

The LLM factory

app/agents/llm.py centralizes the model client. get_llm() builds a ChatGoogleGenerativeAI (Gemini) from GEMINI_API_KEY, with an optional per-agent set of LangSmith tags/metadata. Importing the module first imports app.config (loading .env) and calls init_langsmith(), so tracing is live before any call.

with_retry decorates every node function: it retries up to 3 times with exponential backoff, and — crucially — if all attempts fail it appends the error to state["errors"] and returns instead of raising.

Why never let one node crash the graph?

A LangGraph run touches multiple LLM calls. If a single flaky call raised, the whole pipeline would abort and the PM would see a 500. By catching at the node boundary and recording the error in state, the graph keeps moving and downstream code can degrade gracefully (see section 11).

The thin-wrapper agent pattern

Every agent node follows the same three-step shape:

1. prompt = PROMPT_MD.format(<fields from state>, catalog=catalog_summary())
2. result = get_llm().with_structured_output(Schema).invoke(prompt)
3. persist via a service (only if experiment_id is present), return {state_key: result}

with_structured_output(Schema) makes Gemini emit an object that parses directly into a Pydantic model — no fragile JSON string parsing — and because those schemas are catalog-validated, the model is forced to emit supported ids. Persistence is gated by maybe_session(state) (app/agents/db.py), which yields a DB session only when experiment_id is set.

The six agents

The narration boundary, concretely

In validation_agent, the rule engine produces the decision and score; the LLM is only asked to explain it, and its output updates the deterministic result's narration fields. In explanation_agent, decide_recommendation() calls the shared recommendation engine to pick scale/continue/stop/rollback, and the LLM only writes the rationale paragraph around that fixed category. In report_agent, business impact and the recommendation string are computed in Python; the LLM writes prose. The model can never change a verdict.

Prompts as versioned Markdown

Prompts live in app/prompts/*.md and are templated with str.format. They are written with real prompt-engineering discipline: a strong persona, explicit reasoning steps, hard rules ("every metric MUST be a catalog id, copied verbatim"), output-format requirements matching the Pydantic schema, and a worked example. Because they're plain files, they're versioned and reviewable independently of code.

9. Deterministic decision engines

These three engines are the trustworthy core. They are pure, unit-tested, and never call an LLM.

9.1 Rule engine (app/rules)

A small, configurable engine evaluates JSON rule sets against a nested context using dot-path field access. Each rule has a when condition tree (leaf operators plus and/ or/not composites), an on_match and on_mismatch outcome, and a priority. Operators (eq, gt, between, regex, is_true, …) live in a registry and are added via a decorator, so new rule types need no engine changes.

Two rule sets ship, each loaded by a cached factory:

  • validation_rules.json: 11 rules — traffic split sums to 1.0, both arms get traffic, audience present, primary metric defined (all reject on failure), plus warn-level checks (sample size ≥ 1000, snake_case flag name, guardrail present, confidence ≥ 0.90). Aggregation: any reject wins, else the highest-priority active decision, else approve.
  • recommendation_rules.json: 5 rules — rollback on a significant guardrail regression (priority 100), scale when variant wins with ≥95% confidence and ≥5% lift and no regression, stop when control wins or the sample is exhausted without significance, else continue. Here the highest-priority matched rule wins.
Why JSON-driven rules instead of if/else?

Business rules change often and are the thing a non-engineer most wants to inspect or tweak. Externalizing them into declarative JSON with priorities makes the policy auditable, testable in isolation, and editable without touching Python — while the engine guarantees consistent evaluation and a human-readable explanation for every decision.

9.2 Statistics engine (app/statistics)

compute_statistics(...) takes cumulative per-arm counts and returns a StatisticsOut: control/variant conversion rates, relative lift, a two-proportion z-test (z-score and two-sided p-value via SciPy), confidence = 1 − p, a winner (control/variant/inconclusive), and a significance flag. It is intentionally pure: same inputs, same output. A winner is only declared when confidence clears the threshold (default 0.95) and the test is computable.

9.3 Simulation engine (app/simulation)

generator.py produces synthetic traffic with pure functions and a deterministic RNG: seeded_rng(experiment_id, tick_index) means replaying a simulation yields the exact same series. Per tick it draws new users (Poisson), conversions (Binomial at the arm's rate, where variant rate = baseline × (1 + expected_lift)), revenue (LogNormal), bounces, and per-guardrail values around each metric's catalog baseline. Setting guardrail_regression=True biases the variant to look worse, to demo the rollback path.

scheduler.py wraps APScheduler. For each RUNNING experiment, every N seconds run_one_tick loads the latest snapshot, draws the next tick, computes statistics, runs the recommendation engine, inserts a new Metrics row, and — when the sample size is reached — marks the experiment COMPLETED and deregisters the job. It is thread-safe, idempotent per experiment (max_instances=1), and knows nothing about LangGraph.

Why a deterministic simulator?

This is a decision-support POC without real production traffic. A seeded simulator gives a realistic, animated metrics stream for the dashboard and makes demos and tests fully reproducible. The statistics engine that consumes it is unbiased, so if you fed it real numbers it would still surface the correct answer — only the input source is synthetic.

10. Human-in-the-loop flow

This is where the API layer, services, and graph combine. Two PM decision points bracket the AI work.

sequenceDiagram actor PM participant API participant HS as hypothesis_service participant G as LangGraph participant DB as SQLite PM->>API: POST /context API->>DB: insert product_context PM->>API: POST /context/{id}/hypothesis API->>HS: generate_review(context_id) HS->>DB: create draft experiment (placeholder) HS->>G: start_experiment(thread_id, state) G->>G: context_agent, hypothesis_agent Note over G: PAUSE before experiment_design_agent G-->>HS: paused state (hypothesis) HS-->>PM: HypothesisReview (metrics pre-checked) PM->>API: POST /experiments/{id}/validate (edited metrics) API->>G: update_state(edited hypothesis) API->>G: resume_experiment(thread_id) G->>G: experiment_design_agent, validation_agent Note over G: PAUSE before simulation_node G-->>API: validation persisted API-->>PM: ValidationResult (score + explanation) PM->>API: POST /experiments/{id}/launch API->>G: launch (status RUNNING) + resume_experiment G->>G: simulation, statistics, explanation, report G->>DB: metrics rows + report API-->>PM: experiment (running/completed) PM->>API: GET /experiments/{id}/metrics, POST /report

Step 1 — Generate the hypothesis review

POST /context/{id}/hypothesis calls hypothesis_service.generate_review. It creates a placeholder draft experiment up front so the graph thread is keyed by a real experiment_id from the first invoke, runs the graph to the first pause, then shapes the paused state into a HypothesisReview: the AI problem statement plus, for each role, the full catalog of eligible metrics with a selected flag marking the AI's picks.

Why return the whole catalog, not just the picks?

The UI renders a pre-checked checklist the PM can adjust. Returning every eligible metric with a boolean means the frontend needs no catalog knowledge, and the return payload doubles as the exact shape the PM sends back — a clean, symmetric contract.

Step 2 — Apply edits and validate

POST /experiments/{id}/validate accepts an optional HypothesisMetricUpdate. Its validators enforce that the lists cover exactly the catalog's eligible ids, that exactly one primary is selected, and that the primary isn't also secondary. apply() rebuilds the hypothesis through the Hypothesis schema (re-validating every invariant), the route patches the paused thread via update_state and resumes it — running design then validation — and returns the persisted ValidationResult. If no body is sent (the manual path), it just runs the rule engine directly.

Step 3 — Launch to completion

POST /experiments/{id}/launch checks the snapshot. For a graph-driven experiment paused before simulation, it flips status to RUNNING and resumes the graph all the way to END (simulation → statistics → explanation → report), each node persisting via its service. For a manual experiment it instead registers a live background simulation job. Afterward, GET /experiments/{id}/metrics serves the dashboard snapshot and POST /experiments/{id}/report persists the executive report.

11. Resilience & error handling

The system is designed to keep producing a sensible answer even when the LLM is unavailable (rate-limited, a deprecated model, or no key at all).

Deterministic validation score

Normally the validation agent's LLM enrichment sets validation_score. But validation_service.deterministic_score() computes a launch-readiness score from the rule result alone — banded to match the prompt's guidance (reject < 0.4, warn ~0.5–0.7, approve ≥ 0.85). validate() always fills this score and derives warnings from rejected rules before persisting, so the result is never returned with a null score.

LLM enrichment is non-fatal

In validation_agent.node, the deterministic rule result is computed first, then the LLM call is wrapped in try/except. On any failure it keeps the deterministic result (score and explanation intact) and records the error in state["errors"] instead of dropping the validation.

The validate endpoint's fallback guard

After resuming the graph, the route checks whether experiment.validation is a non-empty dict before trying to parse it. If the agents failed to persist a valid result (e.g. the Gemini quota was exhausted), it falls back to validation_service.validate() — which also fills the score — instead of raising a 500.

Why so much defense around the LLM?

The LLM is the least reliable dependency in the stack — quotas, model deprecations, transient network errors. Because every real decision is already deterministic, the LLM being down should only cost you the narration, never the answer or a working endpoint. Layering the fallback at the service, agent, and route level means no single failure point can turn a valid experiment into an error.

Typed error hierarchy

app/utils/errors.py defines AppError subclasses each carrying an HTTP status and code: NotFoundError (404), ValidationError (422), ConflictError (409, illegal lifecycle transitions), LLMError (502), RuleEvaluationError / SimulationError (500). The single handler in main.py renders them all consistently.

12. Observability & LangSmith

Because the agents run through LangChain inside LangGraph, exporting the LANGCHAIN_* environment variables makes every LLM call and graph node trace to LangSmith automatically — no per-call wiring. init_langsmith() (called on import of the LLM layer) is idempotent and only turns tracing on when an API key is present, so local dev and tests don't spam failed ingestion requests.

get_run_config(run_name, thread_id, agent) attaches tags and metadata (like the thread id) to a run so traces are filterable per experiment and per agent. Two optional callback handlers, TokenMonitor and LatencyTracker, aggregate token usage and per-call latency for a local cost/latency summary.

Logging (app/logging_config.py) installs one stdout handler with a consistent format, reads its level from LOG_LEVEL, and quiets noisy libraries (httpx, urllib3, APScheduler).

Why tracing matters here

An agent pipeline is a black box when it misbehaves — you need to see the exact prompt, the structured output, token cost, and which node failed. LangSmith gives that timeline for free, and the per-agent tags make it easy to answer "which agent is slow / expensive / hallucinating?".

13. Evaluation harness

app/evaluation/ is a standalone quality harness for the six agents. It runs the real agent nodes but can swap in a deterministic fake LLM (fake_llm.py), so it needs no API key and never calls Gemini or LangSmith in offline mode.

Four deterministic evaluators score each output on a 0–1 scale:

  • schema_validity — does the output parse into the correct Pydantic schema?
  • completeness — are required fields present and non-empty (e.g. guardrails non-empty)?
  • correctness — rule-based consistency (traffic split sums to 1.0, score consistent with the rule decision, valid recommendation category, …).
  • relevance — keyword/heuristic coverage against each example's expected keywords.

run_eval.py offers an offline mode (default, CI-friendly) and an online mode (real Gemini, optional LLM-as-judge and LangSmith logging). Run it with python -m app.evaluation.run_eval.

Why an offline eval harness?

It lets the team measure agent quality on every change — in CI, for free, deterministically — without spending tokens or depending on network/model availability. The same real node code runs; only the model is faked, so the plumbing (prompt formatting, structured output, persistence) is genuinely exercised.

Example: create a context

curl -X POST http://localhost:8000/context \
  -H "Content-Type: application/json" \
  -d '{
    "business_goal": "Increase checkout completion",
    "website": "shop.example.com",
    "current_flow": "cart -> shipping -> payment",
    "feature": "checkout",
    "pain_point": "68% of users drop off at the shipping step"
  }'

Example: generate the hypothesis review

curl -X POST http://localhost:8000/context/1/hypothesis

Returns a HypothesisReview: thread_id, experiment_id, experiment_name, hypothesis, problem_statement, and three metric lists (primary_metric, secondary_metrics, guardrail_metrics), each an array of {id, label, selected}.

Example: apply edited metrics and validate

curl -X POST http://localhost:8000/experiments/1/validate \
  -H "Content-Type: application/json" \
  -d '{
    "primary_metric": [
      {"id":"checkout_conversion","selected":true},
      {"id":"add_to_cart_rate","selected":false},
      {"id":"signup_completion_rate","selected":false},
      {"id":"search_click_through","selected":false},
      {"id":"revenue_per_user","selected":false}
    ],
    "secondary_metrics": [
      {"id":"add_to_cart_rate","selected":true},
      {"id":"search_click_through","selected":false},
      {"id":"revenue_per_user","selected":true},
      {"id":"average_order_value","selected":false},
      {"id":"session_duration","selected":false}
    ]
  }'
Contract gotcha

The primary_metric and secondary_metrics lists must each cover exactly the catalog's eligible ids for that role, with exactly one primary selected, and the primary cannot also be selected as secondary. Guardrails are not part of this body — sending them yields a 422.

15. Setup, running & troubleshooting

Prerequisites

  • Python 3.12+ for the backend.
  • Node 20+ (Vite 8) for the frontend.
  • Optional: a Gemini API key for real LLM calls; a LangSmith key for tracing.

Backend

cd backend
make install                 # create .venv + install pinned deps
cp .env.example .env         # add GEMINI_API_KEY / LANGCHAIN_* if you have them
make check                   # import + init_db sanity check
make run                     # uvicorn app.main:app --reload on :8000

Then open http://localhost:8000/docs (Swagger) and /health. The SQLite file backend/experiment.db is created on first startup (git-ignored). To create it explicitly: 

python -c "from app.database import init_db; init_db(); print('created experiment.db')"
python -c "from app.database import engine; from sqlalchemy import inspect; print(inspect(engine).get_table_names())"

Troubleshooting (issues actually hit during development)

SymptomCause & fix
Gemini 404 for the model / blank hypothesisThe default model isn't available to a new key. Set GEMINI_MODEL=gemini-flash-latest in .env and restart.
validation_score null / validate 500LLM enrichment failed silently. Fixed by the deterministic score + non-fatal enrichment + endpoint fallback (section 11). Restart the server so it picks up the change.
Frontend won't start (styleText / native binding)Vite 8 needs Node 20+. Install Node 22 via nvm; do a clean node_modules reinstall (OneDrive can lock files).
Statistics / report all nullThe experiment hasn't simulated yet. Launch it (graph resume or live scheduler) so metrics rows exist before requesting stats/report.
Endpoint ignores schema changesStale --reload process. Stop and restart uvicorn.
